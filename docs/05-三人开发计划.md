## 4. 每日节奏

### 上午同步，不开长会

三人在 GitHub Project 更新：

```text
Yesterday：完成了什么，PR 链接
Today：当前唯一 In Progress Issue
Blocked：需要谁在什么时间前决定什么
Risk：是否影响 RC 或演示
```

同步控制在 15 分钟内。结论写回 Issue，聊天记录不作为最终需求。

### 开发窗口

- A、B 各自只推进一个功能 Issue。
- 尽早推 Draft PR，让接口和迁移可见。
- A/B 每完成一个可验证步骤或最长 90 分钟创建 checkpoint commit 并推送；推送后更新 Draft PR。
- 公共类型或 API 先合并契约 PR，再并行实现。
- C 优先 Review 昨日 PR、复现缺陷和维护绿色构建。

### 每日下午集成

- 16:00 前提交希望当日 Review 的 PR。
- 紧急测试不必等到 16:00，开发者可随时评论 `[READY_FOR_QA] <commit SHA>` 请求 C 拉取指定版本。
- C 运行定向验收，17:30 前给出通过或明确问题。
- A/B 在当天修复 P0/P1；P2 建 Issue，不临时扩大 PR。
- 主分支每日结束时必须可启动。

## 5. Codex 工作隔离

- 三人使用独立 clone 或独立 Git worktree，禁止共用同一个未提交工作目录。
- 每个 Codex 任务只处理当前 Issue，不同时修改他人分支。
- 给 Codex 的提示词必须包含 Issue、分支、允许修改路径和验证命令。
- Codex 输出的假设必须写入 PR；业务假设未经确认不得进入代码。
- A/B 不把未提交文件直接发送给 C；Review 以 GitHub PR commit 为准。
- C 不测试开发者本地未提交状态，只测试 PR 中明确标记的 commit SHA。

## 6. 契约先行

出现以下情况时先做小型契约 PR：

- A 页面依赖 B 尚未完成的 API。
- B 需要改变 A 正在使用的 DTO。
- 数据库迁移影响两个 feature。
- Coze Skill 需要新增写操作类型。

契约 PR 只包含：类型、Schema、接口文档、mock 和失败用例，不同时塞入完整业务实现。合并后 A/B 分别实现客户端和服务端。

## 7. 交接清单

开发者将 PR 交给 C 前必须提供：

- Issue 与验收标准链接。
- 关键实现说明和故意未做内容。
- 本地执行的命令及结果。
- 演示账号、角色和最短复现步骤。
- 涉及的迁移、种子数据和回退方式。
- UI 截图或短视频。
- 权限、幂等、撤销和 Coze 降级的测试说明。

C 完成 QA 后必须回写：

- 测试 commit SHA 和环境。
- 通过／失败的验收项。
- 发现问题的严重度、复现步骤和证据。
- 是否允许进入 `main` 或 RC。

## 8. RC 冻结规则

- 第 9 天结束前从 `main` 选定 RC commit。
- 冻结后只合并 P0/P1 修复、构建修复和演示数据修复。
- 每个冻结期修复必须有回归测试和 A/B 或 C 的交叉 Review。
- 每次修复后重新执行受影响端冒烟；币账、权限或数据库变更触发完整回归。
- 第 10 天构建只使用已打标签 commit，不从本地脏工作区构建。

## 9. 进度判定

任务只有满足以下条件才算 Done：

- PR 已合并到 `main`。
- CI 通过。
- C 已执行验收并记录证据。
- 文档与契约已同步。
- 没有未记录的 P0/P1。

“Codex 已完成代码”或“开发者本地能运行”都不等于 Done。

# 09｜实时协作与测试反馈规范

**状态：强制执行**  
**适用对象：开发者 A、开发者 B、质量与构建负责人 C**

## 1. 目标

开发者 A、B 不等到整个功能完成才上传。开发过程中持续把可验证 checkpoint 推送到 GitHub 功能分支并维护 Draft PR，让 C 能随时拉取明确版本测试、反馈和复测。

“实时”不表示每次保存文件都提交，而表示：

- 第一个有效 checkpoint 立即推送。
- 之后每完成一个可验证小步骤立即推送。
- 连续开发期间最长 90 分钟必须形成一次状态更新；若还不能安全提交，应在 PR 说明阻塞原因和当前状态。

## 2. 唯一协作对象

- Issue：需求和验收标准。
- 功能分支：A/B 的持续代码历史。
- Draft PR：C 查看进度、测试和反馈的中心。
- Commit SHA：每次测试结论对应的唯一版本。

聊天截图、本地压缩包和未提交工作区不能作为 C 的测试输入。

## 3. A/B 开工流程

1. 确认可以读取公开仓库的 Issues，并已获得需要的协作权限。
2. 在目标 Issue 留言：角色、预计开始时间、预计首个 checkpoint。
3. 从最新 `origin/main` 创建 Issue 分支。
4. 完成第一个有意义的最小变更并运行定向检查。
5. 创建 Conventional Commit 并推送分支。
6. 立即创建 Draft PR，关联 Issue。
7. 在 PR 中维护当前进度、验证结果、下一步和已知问题。

示例：

```bash
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c feat/1-project-foundation
```

## 4. Checkpoint 标准

一个合格 checkpoint 必须：

- 只包含当前 Issue 范围。
- 有明确目的，可以通过提交信息理解。
- 尽可能通过当前可运行的 lint、typecheck 或定向测试。
- 不包含密钥、真实学生数据、调试转储和构建产物。
- 不覆盖其他开发者未合并工作。
- 在 PR 中说明尚未完成或暂时失败的检查。

适合形成 checkpoint 的时机：

- 工程配置可以启动。
- 一个公共类型或 API 契约完成。
- 一个页面状态或服务端函数完成。
- 一个迁移与 RLS 测试完成。
- 一个 Review 问题修复完成。

不适合提交：

- 代码无法解析且没有隔离在未引用草稿中。
- 临时注释掉安全检查。
- 混入另一个 Issue 的顺手修改。
- 仅为了满足时间要求制造无意义空提交。

## 5. 提交与推送频率

优先顺序：

1. 完成可验证步骤，立即 commit + push。
2. C 提出 P0/P1 修复后，完成修复与回归立即 push。
3. 连续开发 90 分钟仍无可提交结果，在 Draft PR 评论当前进度、阻塞和预计下个 checkpoint，不制造坏提交。

提交示例：

```text
feat(platform): initialize Expo workspace
test(auth): add linked family RLS cases
fix(bank): prevent duplicate fine deduction
```

首次 push：

```bash
git push -u origin feat/1-project-foundation
```

后续 push：

```bash
git push origin feat/1-project-foundation
```

禁止 force push。C 开始测试后，历史 SHA 必须保持可追溯。

## 6. Draft PR 实时状态

Draft PR 描述顶部维护：

```text
当前阶段：实现中 / 等待 QA / 修复中 / 等待复测 / 可转 Ready
最新 checkpoint：<SHA>
当前可验证内容：<内容>
已通过检查：<命令>
尚未完成：<内容>
已知问题：<内容>
下一步：<内容>
```

每次重要 push 后更新 `最新 checkpoint` 和验证结果。不要每次覆盖历史测试评论，历史 SHA 结论保留在 PR 时间线中。

## 7. 固定协作信号

### A/B 请求测试

```text
[READY_FOR_QA] <commit SHA>
范围：<本次可测试内容>
账号／角色：<合成演示账号角色>
步骤：<最短路径>
本地验证：<命令与结果>
已知限制：<限制>
```

### C 测试通过

```text
[QA_PASS] <commit SHA>
环境：<桌面Web/平板Web/390px手机Web/数据库>
通过：<验收项>
命令：<实际命令>
未测：<边界>
结论：允许继续开发 / 可转 Ready
```

### C 测试阻塞或失败

```text
[QA_BLOCKED] <commit SHA>
严重度：P0 / P1 / P2
环境：<环境>
复现步骤：<步骤>
预期：<预期>
实际：<实际>
证据：<脱敏日志、截图、request_id>
```

### A/B 推送修复

```text
[FIX_PUSHED] <new commit SHA>
对应问题：<PR 评论链接或问题摘要>
根因：<根因>
修复：<修复>
回归：<命令与结果>
请复测：<范围>
```

## 8. C 的持续测试流程

1. 只测试 A/B 明确标记的 SHA。
2. 拉取 PR 分支并记录当前 HEAD。
3. 先运行定向检查，再运行目标角色路径。
4. 将结论按固定协作信号写回 PR。
5. A/B 推送新 SHA 后，按受影响范围决定增量复测或完整回归。

示例：

```bash
gh pr checkout <PR_NUMBER>
git fetch origin
git rev-parse HEAD
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
pnpm test
```

C 不在 A/B 分支上悄悄改代码。发现问题后：

- 普通业务问题退回原作者。
- CI、测试、构建或跨模块阻塞问题由 C 建独立 `fix/*` 分支和 PR。
- C 的修复 PR 必须由 A 或 B Review。

## 9. 并发规则

- A、B 各自最多一个 `In Progress` 功能 Issue。
- 同一文件或公共契约即将被两人修改时，先在 Issue 中声明所有权。
- 公共 DTO、Schema 或迁移先通过契约 checkpoint 合并，再并行实现。
- A/B 不互相向对方功能分支推送，除非分支所有者在 PR 明确授权。
- 解决冲突后必须形成独立 checkpoint，并告知 C 冲突涉及路径。

## 10. 何时转为 Ready for Review

Draft PR 只有满足以下条件才能转为 Ready：

- Issue 验收标准已经全部实现。
- lint、typecheck、相关测试通过。
- 数据库迁移、权限和回退说明齐全。
- UI 有目标端证据。
- 最新 SHA 已请求 C 测试。
- Draft PR 的未完成列表为空。
- 没有未记录的 P0/P1。

C Review 和 QA 通过后才允许合并；旧 SHA 的 `QA_PASS` 不能替代新 SHA 复测。

## 11. GitHub 套餐限制下的执行

当前仓库的分支保护以 GitHub 实际配置为准；无论平台是否强制，团队均遵守以下规则：

- A/B 绝不直接 push `main`。
- A/B 绝不 merge 自己的 PR。
- C 负责合并已经通过 QA 的 A/B PR。
- C 自己的修复 PR 由 A 或 B Review 和合并。
- 只允许 Squash Merge，仓库已关闭普通 Merge Commit 与 Rebase Merge。

仓库管理员应按 `docs/04` 启用强制 PR、Review 和必需 CI 检查；若平台配置暂时不可用，仍由团队流程强制执行。

## 12. 实时协作检查表

### A/B

- [ ] 已接受邀请并领取 Issue。
- [ ] 分支来自最新 `main`。
- [ ] 首个 checkpoint 已 push。
- [ ] Draft PR 已建立并持续更新。
- [ ] 每次请求 QA 都提供具体 SHA。
- [ ] 没有 force push 或直接 push main。

### C

- [ ] 测试前记录 SHA。
- [ ] 测试环境和命令写回 PR。
- [ ] 失败提供可复现证据和严重度。
- [ ] 新 SHA 根据影响范围复测。
- [ ] 只合并最新已验证 SHA。
